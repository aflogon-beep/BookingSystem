# Arquitectura

## Vista general

```
Cliente (móvil/web) ──▶ Next.js en Vercel ──▶ Supabase (Postgres + Auth + Storage)
                            │   ▲
                            ▼   │ webhooks firmados
                          Stripe Checkout
                            │
                          Resend (emails)
```

- La web pública y el panel son la misma app Next.js, en grupos de rutas `(public)` y `(panel)`.
- La lógica de negocio pura vive en `src/lib/domain/`. Las operaciones atómicas (bloquear plazas, confirmar pago, generar salidas) viven en funciones SQL.
- Las migraciones de `supabase/migrations` se aplican solas en Supabase cloud al fusionar en `main` (workflow `.github/workflows/migraciones.yml`, `supabase db push`; también se lanza a mano desde Actions). Usa los secretos de GitHub `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD` y `SUPABASE_PROJECT_ID`. Las seis primeras (hasta `20261009160000_bookings`) se aplicaron a mano en el SQL Editor; `supabase/applied-by-hand.sql` las detecta y el workflow las marca como aplicadas para no repetirlas. Nadie pega SQL a mano.
- Un cron diario (Vercel Cron, `vercel.json`, 03:00 UTC) llama a `/api/cron/generar-salidas`, que ejecuta `generate_sessions(hoy, hoy + 120)` con service role. Solo entra con `Authorization: Bearer $CRON_SECRET` (variable de entorno de Vercel, al menos 16 caracteres). Otro cron diario (09:00 UTC) llama a `/api/cron/recordatorios` con el mismo secreto (ver «Emails»).

## Modelo de datos (borrador para la primera migración)

```sql
settings(id int pk default 1 check (id = 1), business_name, currency, timezone default 'Atlantic/Canary',
         languages text[], cutoff_hours int, cancel_hours int, default_capacity int, email, phone)

staff(user_id uuid pk references auth.users, name, role check in ('admin','staff'))

ticket_types(id uuid pk, name, note, takes_seat bool default true, sort int)

         duration_min int, capacity int, min_pax int, pickup bool, color, photo_path,
         active bool default true)

product_prices(product_id fk, ticket_type_id fk, price_cents int check (>=0), pk(product_id,ticket_type_id))

schedule_rules(id uuid pk, product_id fk, weekdays int[], times time[], language,
               valid_from date null, valid_to date null)

product_needs(product_id fk, resource_type check in ('guide','vehicle','equipment'), qty int 1..5,
              pk(product_id, resource_type))   -- sin fila = no necesita ese tipo

sessions(id uuid pk, product_id fk, starts_at timestamptz, ends_at timestamptz, language,
         capacity int, status check in ('open','closed','cancelled'),
         unique(product_id, starts_at))

resources(id uuid pk, name, type check in ('guide','vehicle','equipment'),
          seats int (vehículo: asientos; material: unidades; guía: 1), languages text[] (guías))

session_resources(session_id fk, resource_id fk, period tstzrange, pk(session_id, resource_id))
  -- period copia el horario de la salida (trigger); exclude using gist (resource_id with =,
  -- period with &&) impide que un recurso esté en dos salidas a la vez. Al cancelar la salida
  -- se liberan sus recursos; al cambiarla de hora, se quitan los que ya estén ocupados.

customers(id uuid pk, name, email, phone, created_at)

bookings(id uuid pk, code text unique, session_id fk, customer_id fk,
         status check in ('pending','confirmed','cancelled','expired'),
         payment_status check in ('pending','paid','refunded','invoice'),
         payment_method, channel check in ('web','phone','desk','agency'), agent,
         hotel, notes, total_cents int, paid_cents int,
         hold_expires_at timestamptz, checked_in bool default false,
         stripe_checkout_id unique, stripe_payment_intent, created_at)

booking_lines(booking_id fk, ticket_type_id fk, qty int check (>0), unit_price_cents int,
              takes_seat bool)   -- valores congelados

booking_events(id, booking_id fk, actor, text, created_at)   -- historial, solo se añade
```

Vista `session_availability`: aforo, plazas ocupadas (confirmadas + bloqueos vigentes con `takes_seat`), plazas libres y pasajeros.

## Flujos críticos

**Reserva web**
1. `create_booking_hold` con `FOR UPDATE` crea la reserva `pending` (bloqueo de 35 min).
2. Stripe Checkout caduca a los 31 min.
3. El webhook `checkout.session.completed` llama a `confirm_booking_payment` (idempotente) y se envía el email.
4. La página de éxito verifica también contra Stripe, por si el webhook se retrasa.

**Crear una reserva** (`create_booking_hold(session_id, lines, customer, booking, hold_minutes = 35)`): la única forma de crear reservas. Bloquea la salida con `for update`, calcula las plazas libres (igual que `session_availability` y `lib/domain/availability.ts`) y crea cliente (se reutiliza si repite email y nombre), reserva, líneas con precio y `takes_seat` congelados de la BD, e historial. Código `VT` + 6 caracteres. Canal `web`: `pending` con bloqueo de 35 min, solo productos a la venta y respetando `cutoff_hours`; se llama con service role desde el servidor. Canales del panel (`phone`, `desk`, `agency`): `confirmed` al momento hasta la hora de salida; el estado de pago sale del método (`card_terminal`/`cash` pagada, `invoice` a factura, si no pendiente; `initialPaymentStatus` en `lib/domain/pricing.ts`). Errores: `RB001` sin plazas (HINT = libres), `RB002` la salida no admite reservas, `RB003` entradas no válidas, `P0002` salida no encontrada, `42501` sin permiso, `22023` otros datos. Es `security definer` y comprueba quién llama: canales del panel, solo el equipo; `web`, solo service role. RLS: el equipo lee reservas, líneas e historial y gestiona clientes, pero no inserta reservas a mano y solo edita `checked_in`, `agent`, `hotel` y `notes` (estado, salida y pagos irán por funciones SQL que vuelvan a comprobar plazas); nadie borra reservas (se cancelan); anon no ve nada. Un trigger impide bajar el aforo de una salida por debajo de sus plazas ocupadas (`RB001`).

**Reserva interna** (`/panel/reservas/nueva`): misma función con un canal del panel (`confirmed` directo) y pago según el método elegido. Desde el panel se abre como modal sobre la pantalla actual (rutas interceptadas: slot `@modal` en el layout de `(panel)` con `(.)panel/reservas/nueva`; `[...catchAll]` lo cierra al navegar a otro sitio); al entrar por URL o recargar se ve la página completa. `?salida=<id>` preselecciona producto, fecha y salida; `?fecha=` solo la fecha. Opciones de cobro por canal en `lib/domain/booking-form.ts`: teléfono y mostrador con TPV, efectivo, enlace de pago o «paga allí» (sin método, pago pendiente); agencia con factura o efectivo. La Server Action valida con Zod y llama a `create_booking_hold` con el cliente de sesión: precios, plazas y total salen siempre de la BD.

**Web pública** (grupo `(public)`): `/` lista los productos a la venta (con al menos un precio) y `/experiencias/[slug]` es la ficha con calendario del mes, horarios del día y selector de entradas. Como anon no ve nada en la BD, el servidor lee con service role (`src/app/(public)/data.ts`) solo datos públicos: ajustes de contacto y políticas, productos activos, precios, idiomas de los horarios y plazas libres de `session_availability`. Nunca reservas ni clientes. Se generan en cada visita (`connection()`). La web vende las salidas abiertas, con plazas y que empiezan después de `now() + cutoff_hours` (`isWebBookable` en `lib/domain/storefront.ts`, la misma regla que `create_booking_hold` con canal `web`), hasta el final de las salidas generadas. El estado va en la URL (`?mes=2026-11&fecha=2026-11-14&salida=<id>`) y lo que no se venda se ignora. «Continuar» lleva a `/experiencias/[slug]/reservar?salida=<id>&entradas=<tipo>:<n>,…` (2.2), que vuelve a comprobar todo en servidor.

**Reservar en la web, sin pasarela** (decisión de 2026-10-09; Stripe queda pendiente): `/experiencias/[slug]/reservar?salida=&entradas=` vuelve a cargar la salida y las entradas en servidor (si ya no se vende o no caben, lo dice y vuelve a la ficha) y pide nombre, email, teléfono opcional y hotel si hay recogida, con un campo trampa para bots. La acción `createWebBooking` valida con Zod (`lib/domain/web-checkout.ts`) y llama a `create_booking_hold` con service role, canal `web` y `payment: 'on_site'`: la reserva queda `confirmed`, pago `pending`, sin método ni bloqueo, e historial «Reserva creada · paga allí», y como mucho 10 plazas por reserva (`RB008`, HINT = 10: los grupos, por teléfono). Si el total que vio el cliente ya no coincide con los precios vigentes, la acción no reserva y se lo dice; el equipo la cobra en el manifiesto. Sin `payment` el canal web sigue creando la reserva `pending` con bloqueo de 35 min para cuando llegue Stripe. La confirmación (`/reserva/[codigo]`) solo la ve el navegador que hizo la reserva: una cookie httpOnly guarda los ids de sus 5 últimas reservas; con el código solo da 404. Al terminar se envía el email de confirmación (ver «Emails»).

**Idiomas de la web** (tarea 2.5): la web pública va en español en sus URL de siempre y en inglés con el prefijo `/en` (`/en`, `/en/experiencias/[slug]`, `/en/experiencias/[slug]/reservar`, `/en/reserva/[codigo]`). No hay carpeta `[lang]`: el proxy (`src/proxy.ts`) quita el prefijo, reescribe a la misma página y pone en la petición las cabeceras `x-locale` y `x-public-path` (en la web pública siempre las pone él; en el panel y el login las borra; `getLocale()` solo hace caso a `x-locale` si llega con `x-public-path`). Las páginas leen el idioma con `getLocale()` (`lib/i18n.ts`) y el layout raíz lo usa para `<html lang>`, así que todas las rutas son dinámicas (a tener en cuenta si se activa `cacheComponents`). Los emails aún salen en español: la reserva no guarda el idioma. Textos del catálogo: `products.name_en`, `description_en` y `meeting_point_en` (los guarda `save_product` desde el bloque «En inglés» del editor) y `ticket_types.name_en` y `note_en` (Ajustes · Tipos de entrada). Son opcionales: la web en inglés usa el texto en español si el inglés está vacío (`localizedText`), así que nada se rompe hasta que se traduzcan. Rutas y prefijos en `lib/domain/i18n.ts`; los textos de las dos lenguas en `lib/domain/web-text.ts` (mismo tipo para las dos, un test comprueba que no falte ninguno); importes y fechas con formato británico en inglés («€12.50», «Saturday 14 November»). Todos los enlaces internos llevan el prefijo del idioma (`localizedPath`) y la acción de reservar recibe el idioma para sus errores y para volver a `/en/reserva/…`. El selector ES/EN de la cabecera recarga la página entera (cambia `<html lang>` y el layout no se repinta al navegar). El panel del equipo sigue solo en español (`/en/panel` da 404).

**Emails** (Resend, tarea 2.3): solo con `RESEND_API_KEY` y `EMAIL_FROM` (`«Volcán Tours <reservas@dominio>»`, dominio verificado en Resend) en las variables de Vercel; sin ellas no se envía nada, se avisa en los logs y todo lo demás funciona igual (`parseEmailConfig` en `lib/env.ts`). Las plantillas son puras (`lib/domain/emails.ts`, texto y HTML escapado, en español); el envío y la lectura de datos, con service role, en `lib/email/` (API HTTP de Resend con `Idempotency-Key` = tipo/id de reserva/hora de la salida, por lotes de 100; nunca lanza). Responder a un email va al email de Ajustes. Los emails se apuntan en el historial de la reserva (actor «Sistema»): **confirmación**, al crear una reserva confirmada con email de cliente (web o panel), con `after()` para no retrasar la respuesta; **recordatorio**, el cron de las 09:00 UTC lo envía a las reservas confirmadas de las salidas no canceladas de mañana (hora de Canarias, `reminderWindow`); **cambio de fecha** y **reenvío** desde la ficha de reserva; **cancelación**, al cancelar una reserva o una salida, a las reservas que estaban confirmadas (la acción las lee antes de llamar a `session_set_status`; las web pendientes de pago no se avisan). Recordatorio y cancelación se marcan (`reminder_sent_at`, `cancellation_sent_at`, solo service role) con un `update … where … is null` antes de enviar, así dos ejecuciones no envían dos veces; si el envío falla, se desmarca, pero nada lo reintenta solo (mejor esfuerzo). Si Resend rechaza un lote, se prueba de uno en uno. Un email que falla no rompe nada: se ve en los logs de Vercel.

**Hoy** (`/panel`, `?fecha=` para otro día): KPIs de las reservas confirmadas de las salidas del día (salidas no canceladas, pasajeros, check-in, ingresos = total de confirmadas y pagos pendientes = `payment_status = 'pending'`; las de factura no cuentan), salidas del día con ocupación de `session_availability` y botón «Reservar» (`/panel/reservas/nueva?salida=`), «Requiere atención» (salidas abiertas de hoy a pasado mañana con reservas y bajo el mínimo; la falta de equipo se añadirá con los recursos) y las 7 últimas entradas de `booking_events`. Lógica pura en `lib/domain/today.ts`.

**Manifiesto** (`/panel/salidas/[id]`, desde «Hoy» y desde el calendario): reservas confirmadas y canceladas de la salida (las web pendientes o caducadas no salen), KPIs (ocupación, presentados, entradas por tipo, pendiente de cobro), check-in, «Marcar todos», cobro en destino (efectivo o TPV), «Copiar» como texto y, en el lateral, estado y aforo de la salida. El equipo no puede cambiar a mano pagos, estado de reservas ni historial, así que todo pasa por funciones SQL `security definer` que comprueban `is_staff()` y escriben en `booking_events` con el nombre de quien lo hace: `booking_set_checked_in`, `session_check_in_all`, `booking_collect_payment` (solo confirmadas con pago `pending`; `RB005` si no) y `session_set_status` (toma la salida con el mismo cerrojo que `create_booking_hold`; cancelar la salida cancela sus reservas confirmadas y pendientes, y reembolsa lo cobrado, ver «Ficha de reserva»). El aforo se cambia con un `update` directo que marca `capacity_custom`; el trigger impide bajarlo de las plazas ocupadas (`RB001`, HINT = ocupadas). `RB004`: check-in de una reserva no confirmada. Una salida cancelada no se reabre (`RB006`) y no se cancela una que ya ha empezado (`RB007`); un trigger impide cancelarla con un `update` directo, y el check-in directo está revocado. Debajo, «Equipo asignado» (ver «Asignación de recursos»).

**Ficha de reserva** (`/panel/reservas/[codigo]`, desde el nombre en el manifiesto y en la actividad de «Hoy»; en el prototipo es un panel lateral): datos, pago, contacto, notas internas (se guardan al salir del campo, `update` directo), historial, cobrar, check-in, reenviar la confirmación, cambiar de fecha y cancelar. Lógica pura en `lib/domain/booking-detail.ts`. Igual que el manifiesto, los cambios van por funciones `security definer` que comprueban `is_staff()` y escriben historial:
- `booking_cancel(booking_id, refund = true)`: cancela una reserva confirmada o pendiente cuya salida no ha empezado (`RB009` si ya está cancelada, `RB007` si la salida empezó). Con `refund` y la reserva pagada, pago `refunded` e historial «Reembolsado X · método». Sin pasarela, eso registra que el equipo devuelve el dinero en efectivo o por TPV; con Stripe, el reembolso online se pedirá antes de llamarla. La ficha propone reembolsar dentro del plazo de cancelación gratuita de Ajustes y no reembolsar fuera de él. Devuelve los céntimos reembolsados.
- `booking_move(booking_id, session_id)`: mueve una reserva confirmada a otra salida del mismo producto, a la venta, sin empezar y con plazas para sus entradas con plaza (`RB001`, HINT = libres; `RB002`; `22023` misma salida u otro producto). Entradas y precios no cambian. Deshace el check-in y borra `reminder_sent_at` para que llegue el recordatorio de la nueva fecha. La ficha ofrece las salidas de los próximos 30 días (40 como mucho).
- Las dos bloquean la salida y después la reserva (`lock_booking_with_session`, las dos salidas en orden de id al mover), igual que `create_booking_hold`, y toman el cerrojo de `generate_sessions` en modo compartido. `session_set_status` cancela ahora cada reserva con la misma función interna (`cancel_locked_booking`), así que cancelar una salida también reembolsa lo cobrado. Las funciones internas (`cancel_locked_booking`, `lock_booking_with_session`, `payment_method_label`) no se pueden llamar desde la API.
- Emails: al cancelar, aviso de cancelación (solo si estaba confirmada); al mover, aviso de cambio de fecha; «Reenviar» manda otra vez la confirmación (con otra clave de idempotencia).

**Asignación de recursos** (tarea 3.2): `product_needs` dice cuántos guías, vehículos y material pide cada salida. `assign_session_resources(session_id, replace)` (interna, no se llama desde la API) rellena los huecos: guías que hablan el idioma de la salida; el vehículo más pequeño con asientos para el aforo (si ninguno llega, el más grande libre); el primer material libre; nunca un recurso ocupado en otra salida que se solape; a igualdad, el más antiguo. Devuelve cuántos faltan. La llama un trigger de `bookings` cada vez que una reserva queda confirmada (nueva, confirmada después o movida), solo si la salida aún no tiene nada asignado, y el botón «Auto» del manifiesto (`session_auto_assign`, equipo, sustituye todo). En el manifiesto, «Equipo asignado» tiene un desplegable por unidad («Guía 1», «Vehículo 1»…) con avisos (ocupado, sin el idioma, pocos asientos); cada cambio guarda el equipo entero con `session_set_resources(session_id, ids)` (security invoker, RLS del equipo). Las tres toman el mismo cerrojo para no elegir a la vez el mismo recurso. Si aun así hay choque, la restricción de exclusión manda: a mano da `23P01` («Ya está en otra salida a esa hora») y en la automática el hueco queda vacío, sin hacer fallar la reserva. `session_missing_resources(session_id)` cuenta lo que falta. Lógica de huecos y avisos en `lib/domain/assignment.ts`.

**Reservas y Clientes** (tarea 3.4): vistas `booking_list` (reservas confirmadas y canceladas con salida, producto, cliente, pasajeros, entradas en JSON y `search_text`; sin las web con tarjeta que nunca se confirmaron, como el manifiesto; las de «paga allí» canceladas sí salen) y `customer_list` (clientes con al menos una reserva de esa vista: reservas, pasajeros y gasto sin canceladas, última salida), las dos `security_invoker` (solo el equipo, por la RLS de las tablas). `/panel/reservas` lleva el estado en la URL (`?pestana=proximas|hoy|pendientes|pasadas|canceladas|todas&q=&producto=&canal=&mostrar=`); `bookingListQuery` (`lib/domain/booking-list.ts`) traduce pestaña y filtros a filtros de PostgREST, la búsqueda es un `ilike` sobre `search_text` con los comodines escapados y se muestran 60 (más con «Mostrar más», hasta 600; a partir de ahí, afinar filtros o CSV). Los totales de la cabecera y el CSV (`/panel/reservas/csv`, mismos filtros, todas las filas) se leen por tandas de 1000 porque la API corta ahí, con un tope de 20.000 que da error en vez de recortar. A diferencia del prototipo, que copia el listado al portapapeles, el CSV se descarga como archivo. El CSV es para Excel en español: «;», coma decimal, BOM y celdas que empiezan por `= + - @` con un apóstrofo delante para que no se ejecuten como fórmula. `/panel/clientes` muestra los 150 que más gastan (o los que coinciden con `?q=`) y `/panel/clientes/[id]` su ficha con contacto y reservas.

**Equipo** (`/panel/equipo`, tarea 3.3): por defecto «Dónde están» (`?fecha=` para otro día) y, con `?vista=fichas` (o `?tipo=`), las fichas por tipo y, en Guías, la planificación de esta semana (salidas de cada guía por día, enlazadas al manifiesto). «Dónde están» lee las salidas no canceladas del día con su equipo, plazas ocupadas y lo que les falta (`missingResources` con `product_needs`) y calcula el estado de cada recurso (`resourceStatus` en `lib/domain/whereabouts.ts`): hoy, en ruta, sale en menos de 1 h, libre hasta la próxima o jornada terminada; otro día, cuántas salidas y la primera. En tablet y escritorio es una línea de tiempo (de 8 a 22 h, ampliada a las salidas del día, con la hora actual en rojo); en móvil, tarjetas. La ubicación es la zona del recorrido del producto (o el punto de encuentro). «Asignar pendientes» llama a `sessions_assign_pending(from, to)` (equipo; rango de 2 días como mucho): rellena, sin quitar nada, los huecos de las salidas del día con plazas ocupadas (lo mismo que cuenta «Salidas sin equipo»), con la misma elección que la asignación automática (`fill_session_resources`, interna). Bloquea en este orden: cerrojo compartido de `generate_sessions`, filas de las salidas por id y cerrojo de asignación. No se ofrece en días pasados. A diferencia del prototipo, no rellena salidas sin reservas, para no ocupar guías y vehículos que aún no hacen falta. Devuelve cuántas salidas tenían huecos y cuántos recursos siguen faltando.

**Alta del equipo (Ajustes > Usuarios)**: el admin invita con nombre, email y rol. El servidor crea la cuenta pendiente con `auth.admin.generateLink({ type: 'invite' })` (service role, tras comprobar que es admin) y la fila de `staff` con la sesión del admin (RLS). No se envía email: el panel muestra un enlace `/invitacion?token=…` que el admin comparte. Al abrirlo, la persona escribe su contraseña dos veces y el servidor gasta el token (`verifyOtp`) y la guarda (`updateUser`). Dar de baja borra la fila de `staff` (el trigger protege al último admin) y luego la cuenta de Auth.

**Editor de productos**: el panel envía el producto entero (datos, precios y reglas) a una Server Action que lo valida con Zod contra los idiomas y tipos de entrada de la BD y llama a `save_product`, que lo crea o actualiza en una sola transacción (precios y reglas se sustituyen enteros; el slug se fija al crear y no cambia). La foto se sube desde el navegador al bucket público `product-photos` de Storage (solo el equipo puede subir o borrar, solo JPG/PNG/WebP de hasta 5 MB) con un nombre aleatorio; el producto guarda la ruta y, al sustituirla, el servidor borra la anterior. La vista previa de salidas usa la misma lógica de reglas (`previewSessions`) que tendrá `generate_sessions`.

**Generar salidas** (`generate_sessions(p_from, p_to, p_product_id?)`, idempotente): crea las salidas futuras de los productos activos que piden las reglas, con el aforo del producto. En las abiertas que siguen en las reglas actualiza idioma, hora de fin y aforo, y borra las abiertas futuras que ya no piden (regla cambiada o producto desactivado). Las cerradas o canceladas no se tocan. Si el aforo de una salida se cambia a mano, hay que marcar `capacity_custom = true` y ya no sigue al del producto. Un cerrojo (`pg_advisory_xact_lock`) evita que el cron y un guardado del panel se pisen. Si dos reglas piden la misma hora, gana la primera del editor (`save_product` guarda el orden en `created_at`). Además del cron, el panel la llama para un producto al guardarlo o al cambiar «A la venta». `sessions` no tiene FK a `schedule_rules`: guardar un producto sustituye sus reglas sin tocar las salidas. Una salida con reservas (de cualquier estado) no se borra: si las reglas ya no la piden, se cierra; y con plazas ocupadas no cambia de idioma, hora ni aforo: `create_booking_hold` toma el mismo cerrojo en modo compartido, así que la comprobación no se cruza con una reserva a medias. `bookings.session_id` es `restrict`: un producto con reservas no se puede borrar (se desactiva). Las reglas guardadas antes de la 1.4 tienen el mismo `created_at`: si dos coinciden, el desempate es arbitrario hasta que se vuelva a guardar el producto.

**Calendario** (`/panel/calendario`): lee `sessions` del rango visible (semana de lunes a domingo, o el mes en semanas completas) convertido a instantes con la hora de Canarias. El estado va en la URL (`?vista=mes&fecha=2026-10-14&producto=<id>`) para poder recargar y compartir; la lógica está en `lib/domain/calendar.ts`. La ocupación muestra plazas ocupadas (vista `session_availability`) / aforo sin contar las salidas canceladas. Pulsar un día del mes abre su semana (en el prototipo abre Hoy, que llega en la 1.8) y las tarjetas de la semana abrirán el manifiesto (1.9). El seed genera las salidas de los próximos 120 días para desarrollo y e2e.

**Zonas horarias**: las reglas guardan hora local. `generate_sessions` construye `(date + time) at time zone` con la zona de Ajustes (`Atlantic/Canary`); en TypeScript lo mismo es `localToInstant` (`@date-fns/tz`). Tests en marzo y octubre.

## Decisiones

| Decisión | Motivo |
|---|---|
| Salidas materializadas (no virtuales) | Permite aforo y estado por salida, FK desde reservas e índices rápidos. |
| Funciones SQL para operaciones atómicas | Garantía de no-overbooking bajo concurrencia. |
| Stripe Checkout (no Elements) | Menos superficie PCI y 3DS resuelto. |
| Invitaciones con enlace para compartir (sin email) | Funciona sin configurar SMTP en Supabase. Cuando llegue Resend (2.3) se podrá enviar además por email. |
| Borrar un tipo de entrada borra sus precios | Como en el prototipo: deja de venderse en todos los productos. Las reservas (1.6) lo impedirán con `restrict`. |
| Fotos subidas desde el navegador a Storage | No pasan por el servidor de Vercel (límite de tamaño de las Server Actions). Una foto subida y descartada sin guardar puede quedar huérfana en el bucket. |
| Un solo negocio | Simplicidad. Multi-tenant posible más adelante añadiendo `org_id` y RLS. |
